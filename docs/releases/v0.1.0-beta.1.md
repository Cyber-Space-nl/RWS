# RWS v0.1.0-beta.1 — draft release notes

**Prepared, not published.** This is an experimental beta, not a stable or production-readiness
claim. The first binary package is intended for x86-64 Linux using GNU libc; it is built and tested
on Ubuntu 24.04. Other distributions, CPU architectures and older libc versions are not validated.
Linux 5.6 or later is required for contained static-file opening.

## Included

- `rws-simple` and `rws-comfy`, the shared core linked into each, and the `rws-ws-load` and
  `rws-bench` development tools.
- Static serving, optional TLS, PHP-FPM, native WebSocket echo, metrics and a bounded static cache;
  Comfy additionally includes an HTTP reverse proxy and adaptive WebSocket scheduler controls.
- Configuration examples, project documentation, project MIT license, dependency license inventory
  and collected license/notice files.

## Important limitations

- The `rws` naming change is incompatible with pre-rename services and paths. The installers do
  not migrate old services. Preserve a working backup and migrate configuration deliberately.
- PHP-FPM opens scripts separately from RWS, so trust and isolate site roots and their parent
  directories. Non-Linux static opens lack Linux's race-resistant containment. PHP-FPM integration,
  HTTP/2 and sustained overload need further independent validation.
- TLS uses one certificate pair per process. The HTTP proxy buffers bodies within per-request
  limits, strips client forwarding headers, does not produce trusted replacements and does not proxy
  WebSockets. HTTP/1 header timeouts are not a complete slow-client or memory defense.
- Historical benchmark results describe their measured builds and workloads; they do not measure
  this beta or establish maximum throughput.
- Dependencies have their own licenses. The inventory and collected license/notice files require
  review for the specific distribution and target; their presence is not a legal compliance opinion.

## Installation, upgrades and rollback

The package has standalone executables in `bin/`, but does not install or start a service. In the
directory containing the archive and `SHA256SUMS`, verify and extract it:

```bash
sha256sum -c SHA256SUMS
tar -xzf rws-v0.1.0-beta.1-x86_64-unknown-linux-gnu.tar.gz
cd rws-v0.1.0-beta.1-x86_64-unknown-linux-gnu
sha256sum -c BINARY_SHA256SUMS
bin/rws-simple --version
```

For a systemd installation built from source, use
[UBUNTU_INSTALL.md](../../UBUNTU_INSTALL.md). The existing installers expect the repository layout
and locally built binaries in `target/release/`; do not run them from the standalone archive.

Before upgrades, back up the binary, unit, configuration, logrotate file and site data. Stop the old
service, install the intended binary, review configuration, validate it with `--check`, then start
and verify routing, logs and health. For rollback, stop the service, restore the matched binary,
unit and configuration backups, run `systemctl daemon-reload`, restart and verify. `--check` does
not test service-user permissions, available ports or PHP-FPM reachability. Test this procedure in
an isolated environment first; no in-place upgrade or rollback was validated for this draft.

Do not publish a GitHub release, tag or artifacts until explicitly approved and the independent
validation and license review are complete.

## Build the draft package

On x86-64 Ubuntu 24.04 with Python 3.12, Rust 1.88 or newer, Cargo and the GNU build toolchain,
commit the intended source revision, unset build override environment variables, and run:

```bash
python3 tools/release/assemble.py --output /tmp/rws-beta-1
cd /tmp/rws-beta-1
sha256sum -c SHA256SUMS
```

The output directory must not exist. The script builds each binary separately from `git archive`
of the committed revision, collects an overinclusive Linux normal/build dependency license set,
records build-host information and writes archive and binary checksums. Build-host libc is not a
minimum compatibility guarantee. Review the collected licenses and test the extracted package on
the intended systems. Builds are not claimed to be byte-for-byte reproducible across toolchains.
