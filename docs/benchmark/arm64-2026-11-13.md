# ARM64 static HTTP comparison — 13 November 2026

This is a bounded comparison of RWS Simple, Nginx and Apache serving identical static files.
It is a short exploratory benchmark, not a measurement of peak throughput or an independent
security or performance audit.

## Method

- **Test server:** Oracle ARM64 VM, Ubuntu 24.04.4, two Neoverse-N1 vCPUs and approximately
  11.6 GiB RAM. Other services remained active.
- **Load generator:** separate x86-64 Ubuntu 26.04.1 host with two vCPUs; production services
  remained active. Safety limits bounded its load.
- **Transport:** HTTP/1.1 over a shared encrypted SSH tunnel between the machines. Latency
  includes the tunnel, network and client; the test does not isolate server processing time.
- **Workload:** warm static files of 67 bytes and 4 KiB, 50 keep-alive connections, and offered
  rates of 100 and 600 requests/second. Three eight-second runs per server, file and rate; the
  server order rotated. This is 36 runs in total.
- **Versions:** RWS Simple `0.1.0-beta.1`, built for ARM64 from commit `f859919`, Nginx 1.24.0
  and Apache 2.4.58. RWS used the single-thread runtime and its enabled static cache with the
  default one-second revalidation interval. Nginx used two workers, sendfile, TCP_NODELAY,
  TCP_NOPUSH and an open-file cache. Apache used the event MPM with two processes and 25 threads
  each, keep-alive and sendfile. Nginx's open-file cache and RWS's static cache work differently;
  these are explicit configurations, not proof of exhaustive tuning.
- Before the runs, the servers returned the same status, content type, length and file bytes.
  Some other response headers differed. Fixture SHA-256: 67 bytes
  `600bb39b0233240031526be743b2b8d4e8ed9704ea4f27fc70788ad36bc1d862`; 4 KiB
  `f096faea98dbd73950be903e2a31c5c2f051997b8db5e1eb3b2a390dfd79fa05`.

## Results

The latency cells are **medians of the three run-level percentiles**, in milliseconds; they are
not percentiles pooled across all requests. The achieved rate was 100 or 600 responses/second in
each scenario, equal to its offered rate. In total, 100,800 responses succeeded, with zero
recorded failed responses, failed connections or socket errors. The client counts HTTP 2xx and
3xx responses as successful; latency includes successful responses only.

| File | Offered req/s | Server | p50 ms | p95 ms | p99 ms |
|---|---:|---|---:|---:|---:|
| 67 B | 100 | RWS | 1.24 | 1.96 | 2.74 |
| 67 B | 100 | Nginx | 1.22 | 1.61 | 2.60 |
| 67 B | 100 | Apache | 1.47 | 3.12 | 4.49 |
| 67 B | 600 | RWS | 2.54 | 4.52 | 5.61 |
| 67 B | 600 | Nginx | 2.51 | 3.69 | 5.50 |
| 67 B | 600 | Apache | 2.59 | 3.72 | 4.60 |
| 4 KiB | 100 | RWS | 1.34 | 1.99 | 2.97 |
| 4 KiB | 100 | Nginx | 1.31 | 1.92 | 3.28 |
| 4 KiB | 100 | Apache | 1.43 | 1.97 | 3.01 |
| 4 KiB | 600 | RWS | 0.98 | 1.57 | 2.18 |
| 4 KiB | 600 | Nginx | 1.01 | 1.65 | 2.43 |
| 4 KiB | 600 | Apache | 1.11 | 1.68 | 2.12 |

CPU and proportional set size (PSS) were sampled approximately once per second for each server's
process tree. Monitoring began partway through the series: each 600 req/s scenario has **two**
monitored runs; the 100 req/s scenarios have one or two. CPU is the median of run-average CPU,
with 100% representing one fully used vCPU. PSS is the median of the per-run sampled medians,
not peak memory. The aggregate data contains the exact counts and values.

| File | Offered req/s | Server | Monitored runs | CPU, one-vCPU % | PSS MiB |
|---|---:|---|---:|---:|---:|
| 67 B | 600 | RWS | 2 | 3.3% | 4.87 |
| 67 B | 600 | Nginx | 2 | 3.5% | 5.76 |
| 67 B | 600 | Apache | 2 | 8.7% | 5.40 |
| 4 KiB | 600 | RWS | 2 | 3.6% | 4.88 |
| 4 KiB | 600 | Nginx | 2 | 3.4% | 5.76 |
| 4 KiB | 600 | Apache | 2 | 8.0% | 5.33 |

The short runs, shared hosts, SSH tunnel, different cache implementations and load-generator
behaviour can influence the results. The offered rate caps throughput, so meeting it does **not**
show how much more traffic a server could handle. Differences here should not be generalized to
other workloads or interpreted as a security conclusion.

## Follow-up diagnostic

An additional RWS-versus-Nginx experiment used a different Python asyncio client on the same
Oracle host over loopback. With 50 connections, 600 offered requests/second and five ten-second
runs, the median run-level p95 was 0.220 ms for RWS with the default cache, 0.216 ms for RWS
with a 60-second cache revalidation interval, and 0.222 ms for Nginx. The client shared the
server's CPU and its scheduling can affect results. This experiment does not identify the cause
of the earlier tunnel-test differences, and its numbers should not be compared directly with
the table above.
